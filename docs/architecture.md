# هندسة Mustanad Jo

هذا المستند يصف البنية الحالية كنقطة مرجعية للتطوير، وليس كمواصفات حكومية.

## تدفق الطلب

```text
وصف هدف المستخدم
  -> بوابة نية حتمية (مشروع / سؤال / معاملة شخصية غير مدعومة / غير واضح)
  -> المعاملة الشخصية تتوقف برسالة نطاق ولا تصل إلى استخراج الحقول أو Ollama
  -> /api/intake
  -> استخراج حتمي + استخراج Ollama اختياري
  -> أسئلة الخيارات للحقول الناقصة
  -> /api/journey
  -> محرك القواعد والترتيب الطوبولوجي
  -> رحلة + قائمة مستندات + مقاطع أدلة

إذا كان الهدف خارج القواعد الموثقة
  -> /api/explore
  -> استخراج حتمي سريع للأوصاف الشائعة، وOllama فقط عند الغموض
  -> تثبيت الحقائق الصريحة بقواعد حتمية
  -> اختيار مراحل بحسب الفئة/الموقع/نموذج التشغيل
  -> خطة استكشاف + أدلة إنجاز + مصادر أولية، دون اختلاق متطلبات

سؤال المستخدم من الصفحة الرئيسية أو داخل الرحلة
  -> تطبيع وتقطيع عربي + light stemming + مرادفات + تحمل خطأ إملائي
  -> BM25 موزون + reranking سياقي + عتبة ثقة مطلقة ونسبية
  -> عبارة قصيرة واضحة: جواب extractive فوري من أفضل مقطع
  -> Ollama بصيغة JSON مقيدة
  -> Zod + تحقق معرفات الأدلة + تداخل نص الادعاء + منع الروابط المخترعة
  -> جواب واستشهادات، أو insufficient_evidence
```

يسبق هذه التدفقات تسجيل دخول بجلسة HMAC موقعة ومخزنة كـhash في MongoDB، مع التحقق من حالة الحساب ونسخة الجلسة. طبقة `api-history` تحفظ الطلب والاستجابة للمستخدم الحالي بمفتاح تدفق فريد وتحدّث السجل نفسه. MongoDB إلزامي للمصادقة والحفظ؛ فشل الحفظ يعيد خطأ واضحًا ولا يعرض نجاحًا وهميًا.

الواجهة تفصل صراحةً بين الهدف والسؤال، وتحوّل النص الذي يبدأ بأداة سؤال أو يحتوي علامة استفهام إلى مسار المعرفة. السؤال غير المرتبط لا يدخل wizard ولا يستدعي النموذج إذا لم يجد الاسترجاع دليلًا مناسبًا.

## حدود الوحدات

- `app/`: الصفحات وواجهات HTTP فقط؛ لا توضع قواعد المجال داخل مكونات React.
- `components/`: حالة العرض والتفاعل. تستخدم `lib/client-api.ts` بدل تكرار منطق `fetch`.
- `lib/contracts.ts`: عقود الاستجابات المشتركة بين مكونات الواجهة.
- `lib/intake.ts`: الاستخراج الحتمي، دمج الحقول، التغطية وترتيب الأسئلة.
- `lib/request-intent.ts`: حاجز النية الذي يفصل معاملات الهوية والجواز والرخصة عن مشاريع الأعمال والأسئلة.
- `lib/auth.ts`: جلسة الدخول المحلية الموقعة؛ ليست تكاملًا مع سند أو هوية حكومية.
- `lib/mongodb.ts` و`lib/interaction-history.ts`: الاتصال المطلوب وحفظ/قراءة سجل المستخدم بمفتاح طلب فريد، مع حجب بعض أنماط الأرقام في نص المدخل.
- `lib/rules.ts`: تقييم القواعد، كشف `unknown`، التحقق من الاعتماديات وبناء الرحلة.
- `lib/knowledge.ts`: بوابة نشر المعرفة والفصل بين `demo` و`production`.
- `lib/retrieval.ts`: تطبيع العربية وترتيب المقاطع النصية.
- `lib/explore.ts`: ملف المشروع الاحتياطي ومحرك بناء مسارات الاستكشاف العامة.
- `app/api/explore`: استخراج الملف الديناميكي وتجميع خطة آمنة للحالات غير المدعومة.
- `lib/ai/`: المزود المحلي، prompts، JSON Schema، Zod والتحقق من الاستشهادات.
- `data/`: مصادر ومقاطع وقواعد قابلة للتدقيق خارج كود الواجهة.

## ثوابت يجب الحفاظ عليها

1. اختيار المستخدم أعلى أولوية من النموذج، والاستخراج الحتمي أعلى من التخمين الاحتمالي.
2. `null` من النموذج يعني «لم أجد» ولا يمحو قيمة معروفة.
3. النموذج يشرح فقط؛ القواعد الموثقة هي التي تحدد الإجراء وترتيبه.
4. لا يدخل أي مقطع `pending` إلى وضع الإنتاج.
5. لا تُقبل إحالة إلى مقطع لم يرجعه الاسترجاع.
6. تعطل Ollama لا يعطل الأسئلة أو القواعد أو قائمة التجهيز.
7. لا يُستدعى Ollama افتراضيًا لتحديد نية intake أو ملء حقوله؛ الغامض يطلب توضيحًا بدل تخمين الملابس. ويمكن تفعيل ذلك فقط صراحةً من البيئة.
8. حاجز النطاق يسبق الاسترجاع: أي نشاط أو مدينة أو شكل قانوني مختلف لا يرث سياق الرحلة الحالية ولا يصل إلى Ollama.
9. حاجز النية يسبق استخراج الحقول: المعاملة الحكومية الشخصية لا تتحول إلى مشروع ولا تستدعي AI.
10. فشل MongoDB لا يُخفى؛ يمنع التحقق من الجلسة أو الحفظ، بينما محرك القواعد نفسه مستقل عن الاتصال.
11. لا يُنشر `answer` الحر من النموذج؛ الخادم يبنيه من claims اجتازت تحقق الأدلة النصي.
12. وجود استشهاد صحيح لا يكفي: الادعاء نفسه يجب أن يتداخل مع نص المقطع، وأي URL غير موجود يُرفض.

## إضافة رحلة مستقبلًا

1. أضف قيم النطاق إلى مخططات Zod في `lib/schemas.ts` وأسئلة `lib/intake.ts`.
2. أضف المصدر ثم المقطع الداعم، مع النص والشروط وحالة المراجعة.
3. أضف الإجراء إلى ملف demo أولًا واختبر شروطه واعتمادياته.
4. لا تنقله إلى `data/procedures.json` ولا تجعل المقاطع `reviewed` إلا بعد مراجعة بشرية موثقة.
5. أضف اختبارات للتغطية، الفرع الجديد، ترتيب الخطوات، والمستندات الناتجة.

عند زيادة عدد الرحلات كثيرًا، الخطوة التالية هي تقسيم مخططات النطاق إلى سجل رحلات مستقل، وتوليد الأسئلة والقيم من تعريف الرحلة بدل توسيع enums مركزيًا.

## تحسينات إنتاجية لاحقة

- مخزن دائم وموزع لتحديد المعدل بدل الذاكرة المحلية.
- نقل مصادقة العرض إلى مزود هوية حقيقي عند الانتقال للإنتاج؛ لا يُستخدم دخول demo خارج التشغيل المحلي.
- إضافة إصدارات المعرفة وسجل المراجعات إلى قاعدة البيانات بجانب سجل التفاعلات الحالي.
- بحث BM25 أو embeddings محلية عند نمو المقاطع، مع إبقاء بوابة المراجعة.
- اختبارات متصفح end-to-end ضمن CI.
- مراقبة زمن Ollama ومعدل fallback دون تسجيل نص المستخدم أو بيانات شخصية.
